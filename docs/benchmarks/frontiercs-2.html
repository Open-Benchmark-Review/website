FrontierCS 2

Benchmark creator: FrontierCS Team (Qiuyang Mang, Wenhao Chai et al.)

Original benchmark: frontier-cs.org

Version reviewed: 48 public tasks; leaderboard of Oct. 26, 2026

Verdict: *Flawed

FrontierCS 2 is an agentic benchmark of computer-science R&D. Each of its 48 public tasks deletes the key contribution of a published paper from the authors' own repository. The agent gets 5 hours, with no network access, to rebuild it. A run passes only if its final patch beats the deleted code (the "human reference") on every metric and every held-out workload. The headline leaderboard number is the pass rate, from one run per task and model.1

What we found

  • 23 of the 48 tasks (48%) have a grading defect that can flip a pass or a fail. A benchmark is rated Flawed at 20%.
  • 14 tasks are close to impossible or decided by noise. A run must beat the original code on every workload, with no allowance for timing noise, and on several tasks the original code would fail its own bar.
  • 9 tasks can be passed without a real improvement, because the grader can be gamed or accepts a tie.
  • On 5 tasks the leaderboard mixes runs graded before and after the developers fixed those graders.
  • Each model runs once per task. Where the dataset has repeated runs, 31% of them disagree on pass or fail, and the top two models can't be told apart (p = 0.75).

The developers fixed five exploitable graders within days of release, and we credit them for it. The published leaderboard still reflects the old graders: 72 of the 85 results on those tasks were scored before the fixes.3

Does the ranking hold? Mostly. The order of models largely survives correction. The pass rates, and close comparisons between models, do not.

Representative Errors

  • Reward hacking. A submission changes what gets measured instead of improving the method. In dynamic_tanh, Gemini 4 Argon (Pi)'s counted pass checks sys.argv[0] == "main.py". It runs fast kernels only when the evaluator is timing it, and a different code path when accuracy is scored. The developers patched exactly this behaviour after the runs. In detok_latent_denoising, the same model passes by optimizing its latent codes against the very image being scored.4
  • Exploitable scorers, fixed after the runs. Five scorers could be gamed:
    • parallel_dbscan and batch_local_counting: reusing state across timing rounds.
    • dynamic_tanh: argv introspection.
    • evm_state_checkpoints: moving cost into untimed work.
    • progent_privilege_control: security judged on requested calls rather than executed ones.
    Only the runs that tripped a fix were re-run. Under the developers' own fixed Progent rule, our replay of the final traffic turns three failing runs (Opus 5.5, DeepSeek V4.1 Flash, Qwen 3.8 Max) into passes.
  • The reference cannot pass its own bar. In vllm_llm_serving_optimization, candidates must beat the per-request minimum of three reference captures, with zero margin. A fresh run of the reference itself would need a 1.02–1.69× speedup to clear that bar. In fast_kv_compaction, the reference clears its own accuracy gate 13–17% of the time.
  • Uncalibrated tasks. Two tasks shipped flagged by their own files:
    • representation_frechet_loss tells the agent its "source revision [is] awaiting runtime qualification", and its workloads are marked proposed_uncalibrated.
    • flow_opd ships with release_ready: false and a single reference repetition.
  • False negatives from strict "win every cell" rules. Many tasks require a strictly better result on every workload, with no tolerance, on measurements that are noisy or close to the timing floor:
    • join_tree_rewriting requires a faster median on all 39 queries. None of 638 development submissions cleared all 20 dev queries.
    • runlts_predictor requires wins on all 105 traces. Its own README says a trivial RNG change moves one trace by about 1%.
    • In parallel_radix_sort, a run 7–8% faster on average fails while a run 5% faster passes.
  • Bars that pass without improvement.
    • metaopt_combined_te_gap_search accepts ties against a deterministic reference, so the unchanged reference passes.
    • polygon scores a time that the candidate's own editable code reports.
    • polar_express is beaten by running the paper's own code without its bf16 safety margins.

Outside scoring defects:

  • Harness effect. The same Gemini 4 Argon model passes 54.2% of tasks in Antigravity and 39.6% in Pi (8 vs 1 discordant tasks, p = 0.039). That is larger than the gap between leaderboard ranks 2 and 5.
  • Undisclosed settings. The Antigravity entry, ranked #2 on Kaggle, has no published harness settings in the repo or paper; we recovered them from its traces.
  • Mid-run model switch. One Opus 5.5 run finished on Opus 4.8 after a refusal.
  • Effort settings. Five entries ran at high reasoning effort while the rest ran at max or xhigh.

Total: 23 of 48 tasks (47.9%): 9 false positive, 12 false negative, 2 impossible. Two tasks carry both a false-positive and a false-negative defect. The Flawed threshold is 20%. The verdict holds on narrower counts too:

  • Excluding the five tasks the developers have since fixed, 18 of 48 tasks (37.5%) are affected.
  • Counting only the 8 tasks that are unpassable or unqualified by their own files or by direct computation, plus the five fixed tasks, 13 of 48 tasks (27%) are affected.

Sensitivity of the leaderboard

Correcting the confirmed defects leaves the model order largely intact. The pass-rate levels change: on the 25 tasks without a counted defect, the top model passes 84%.

Rubric

1. Reviewability

Full

NotesEvery task, judge, reference, final patch and trace is public. Four entries added after the paper have no harness recipe or settings in the repo: Gemini 4 Argon (Antigravity), GPT-6.1 Terra, Kimi K3.1 Pro and DeepSeek V4.1 Flash 1017. Their settings can be recovered from the raw request bodies in the released traces.

2. Scoring

Scoring

Flag
Notes23 of 48 tasks (47.9%) are affected; see Errors.

Benchmark Consistency

Flag
NotesOn five tasks the leaderboard mixes runs scored before and after scorer fixes, with no version bump. On evm_state_checkpoints, 14 runs were scored on a 3-workload scorer (reference ≈ 61) and 3 on a redefined 6-workload scorer (reference ≈ 75).

Elicitation

Pass
NotesAgents get 5 hours in modern vendor harnesses. Non-voluntary termination is low for ranked entries; Gemini on Pi lost 10 of 48 runs to provider refusals, but that entry is not ranked on Kaggle. Budgets of 3–8 development submissions on several GPU tasks are tight, but did not decide outcomes.

Bias in Evaluation Setup

Pass
NotesWe found no confirmed material advantage. Each model runs in its own harness. Reasoning effort is high for five entries and max or xhigh for the rest. Refusal handling differs: Pi stops the run, Antigravity retries, and Claude Code falls back to Opus 4.8.

3. Evaluation quality

CheckWhat we found
Runs per model1 run/model. 31% of repeated (task, model) runs in the dataset disagree on pass/fail. #1 vs #2: 6 vs 4 discordant tasks, p = 0.75. The 95% CI for #1 is 43.8–72.9%.
Enough time and computeMostly. Adequate overall; three development submissions on several GPU tasks.
Same agent setup for every modelNo, each model uses its own. The same model scores 54.2% in Antigravity and 39.6% in Pi.
Test data exposure100% of tasks public (since Oct. 20, 2026); reference implementations come from public upstream repos. Reproducing the reference only ties, so it doesn't pass. The private set of 100+ tasks was not reviewed.
Measures what it claimsPartly. "Beats the paper" often means beating a reference outside its design regime. On knn, the bar is a task-authored kernel rather than the paper's code.

Disclaimer

This is a full review of the 48 public tasks; the private set was not reviewed. Most false-negative probabilities are estimates from the pass rules, the measured reference noise and the developers' notes, not fresh reruns. The Progent correction rests on our reconstruction of the final traffic, because per-episode verifier evidence is not released.
