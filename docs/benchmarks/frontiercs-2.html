Summary

FrontierCS 2 tests whether an AI agent can rebuild the key contribution of a published computer-science paper, measured by the share of tasks it passes. In each of its 48 public tasks, the paper's code (the reference) is removed, the agent has 5 hours to rewrite it, and a run passes only if it beats the reference on every metric and every test set.ab

What we found

  • We reviewed all 48 public tasks and found that 15 (31%) had grading errors.
  • On 11 tasks, a run must beat the reference on every single test, by a margin smaller than the reference's own run-to-run noise, so even the reference often fails its own bar.c On one task, Kimi K3.1 Pro's faster server failed because of one slow query out of 2,000.
  • Two tasks can be passed without a better method. Copying the reference passes one, because ties count, and on another, runs tune their output to the very image being scored.
  • Three runs on a task about blocking prompt-injection attacks are listed as failing because blocked attacks were counted as successful ones. By the task's current grader, all three would pass.

Case studies

Three tasks show the two kinds of problem. On the first two, the pass bar is tighter than the reference's own variation. The reference rarely clears its own accuracy bar on KV-cache compaction, and on QuarterPIR a faster server fails on one slow query out of 2,000. On the third, runs tune their output to the image being scored.

KV-cache compaction

The task is to shrink a model's cached context to a tenth and keep its answers, by rebuilding the method of the Fast KV Compaction paper (ICML 2026). The cached context, the KV cache, is the model's working memory of a long document. The grader asks 13 to 20 questions about each of 24 articles, three times over from the shrunken cache, and the worst of the three must come within one question of the reference's median scorejudge/gate.py:9judge/gate.py:209judge/gate.py:245-256.

The reference is never run at grading; its three recorded runs are frozen, and from try to try its scores wobble by a question or so. On 5 of the 24 articles, one of its nine recorded tries falls one question below the bar, and one such try among an article's three fails the whole run. Re-run unchanged, the authors' own method fails the task's accuracy bar about 5 times in 6. Even the full, uncompressed cache, which loses nothing, scores 14 on one article where the bar is 15judge/targets/manifest.json, article 30029.

QuarterPIR

The task is to make each lookup in QuarterPIR, a scheme from a EUROCRYPT 2024 paper that lets a client read a record from a server without the server learning which one, send fewer bytes and run faster. The grader replays each of 2,000 queries five times on the candidate's server and five times on the reference's, takes the median of each five, and requires the candidate to be faster on every queryjudge/table2_metrics.py:305-306.

Kimi K3.1 Pro's serverk31Kimi K3.1 Pro passed every other check and was faster on 1,999 of the queries. On the last one, three of its five replays took 1.56 to 1.94 ms, against 0.87 to 0.94 ms for the reference, so its median came out slower and the run failed. That was in the regrade the leaderboard counts, which graded the same final submission againmetadata/formal-results.json. In the first grading, all five replays of that query were faster than the reference's, and the run was faster on all 2,000. Ten other tasks on this page have a pass bar of the same kind.

Latent-denoising tokenizer

The task is to restore the training from an ICLR 2026 paper that makes an image tokenizer robust. A tokenizer compresses a picture into a short code of tokens and decodes it back. The grader trains each submission briefly, then scores how closely it reproduces held-out photos. A run must beat the reference on quality and on time on each of three workloads.

All errors

Pass bars tighter than the reference's own variation

All 16 errors on this page, on 15 tasks, count toward the 31%. Each task has a pass bar, the rule a run must meet to pass. On these 11 tasks it requires beating the reference on every workload, query or episode, with a tolerance smaller than the reference's own variation from one run to the next, so a real improvement can fail on one unlucky measurement.

  1. The vLLM target is faster than any real run of the reference

    The task is to make vLLM, a widely used server for language models, answer multi-turn agent conversations faster without changing its answers, by rebuilding the scheduler from the Continuum paper (arXiv 2025). The grader never reruns the reference, the authors' own code. It sets a target time for every request instead, the fastest of 3 earlier reference runs with zero margin, so no real reference run can meet it. There are 20 checks, 5 on each of 4 groups of coding-agent (SWE-bench) and tool-calling (BFCL) requests. They cover a geometric mean of latency (an average across requests), the tail latencies that only the slowest 10%, 5% and 1% of requests exceed (p90, p95, p99), and correct answers. Claude Fable 5.1 and GPT-6 Astra pass 19 of the 20, including all 12 tail-latency checks, and miss only the geometric-mean check on the public SWE-bench group.

    Task: vLLM serving (vllm_llm_serving_optimization)

    Where: fable51 (Claude Fable 5.1), astra (GPT-6 Astra), beat_spec.json, fixed-targets.json · 5 sources
    • Task page on frontier-cs.org: "Speed up vLLM serving for multi-turn coding and tool agents." Task summary and paper: the task's metadata file, lines 4–6
    • judge/beat_spec.json:122-126: "per-instance minimum reference latency across three authenticated captures"
    • verifier/fixed-targets.json: each reference run would need to be 1.02–1.69× faster to meet it
    • fable51 Claude Fable 5.1 · 19 of 20 checks; geometric-mean latency on SWE-bench public at 0.86× the target's speed, the only failed check (phase/operator-result.json in the verifier evidence)
    • astra GPT-6 Astra · 19 of 20 checks; geometric-mean latency on SWE-bench public at 0.94× the target's speed, the only failed check

  2. Kimi K3.1 Pro fails QuarterPIR on one slow query out of 2,000

    The task is to make each lookup in QuarterPIR send fewer bytes and run faster. QuarterPIR, from a EUROCRYPT 2024 paper, lets a client read a record from a server without the server learning which one. The server must be faster than the reference on every one of 2,000 queries, each timed as the median of 5 replays. Kimi K3.1 Pro's server takes 0.38–0.71× the reference's time on a typical query. But in the regrade the leaderboard counts, a second grading of the same submission, 3 of 5 replays of one query were slow, which failed the run. The same submission passed its first grading.

  3. The reference rarely clears its own accuracy bar

    The task is to shrink a language model's cached copy of a long document, its KV cache, to a tenth of its size while the model still answers questions about the document, rebuilding the method of the Fast KV Compaction paper (ICML 2026). On each of 24 articles the model answers the questions 3 times, and its worst try must score at least the reference's median minus one question. By our resampling of the reference's saved results, its own method clears that bar only about 1 time in 6. Even the full, uncompressed cache misses it on one article.

    Task: KV-cache compaction (fast_kv_compaction)

  4. Three random robot episodes per group decide quality

    The task is to write the step that picks a robot's next actions in Diffusion Policy (RSS 2023), a controller that pushes a T-shaped block into place in a simulator, so that it runs faster on a CPU. A faster sampler must also match the reference's reward and success rate over 3 simulated episodes in each of 4 groups, each group starting from one position, with no tolerance. With only 3 random episodes, each group passes about half the time, so all four pass about 7% of the time. Gemini 4 Carbon is 16× faster and better when the episodes are pooled, but fails two groups.

  5. The reference's own score varies 11% between runs

    The task is to keep the running feature statistics differentiable for the loss in the Representation Fréchet Loss paper (arXiv 2026), which fine-tunes an image generator toward real images. Quality is a Fréchet distance, a standard measure of how far generated images are from real ones in a feature space (lower is better), taken in 6 feature spaces on 3 training setups. A candidate must beat the reference in all 18 comparisons, but the reference's own score varies by about 11% between runs, and the task's README says it is "awaiting runtime qualification", that is, not yet validated. Gemini 4 Carbon halves the reference's distance yet wins only 16 of the 18 comparisons.

    Task: Fréchet representation loss (representation_frechet_loss)

  6. Lookups must be faster on all 144 workloads, within the noise

    The task is to write a faster binary fuse filter, the compact structure from an ACM JEA 2022 paper that answers "is this key in the set?" with rare false yeses. A run must beat the reference on memory, build time and lookup time in every one of 144 workloads, test sets of different sizes and key types. On the largest filters, where lookups wait on memory, the reference's own lookup time varies by about 2–3% from one measurement to the next, and strong candidates are only 5–14% faster. Three runs fail only on 1 or 2 of the 144 lookup comparisons.

  7. The timed step can measure zero or less

    The task is to make Edlib, a C++ library from a Bioinformatics 2017 paper for comparing DNA or protein sequences, recover the exact alignment between two sequences quickly and in little memory. The grader times only that recovery step, as the fastest of 15 full runs minus the fastest of 15 runs that skip it, and on the most similar sequences the step takes about 0.1 ms. A run must be faster than the reference but above zero. In 19 of the 151 evaluations the agents requested during their runs, the reference's time on some workload came out zero or below, which makes passing impossible. GPT-6 Astra fails the final grade on 1 of 60 workloads.

  8. The 5% speedup bar mostly measures process start-up

    The task is to speed up how egg, an e-graph library from a POPL 2021 paper, restores its internal consistency after rewrites, using the paper's deferred "rebuilding". An e-graph stores many equivalent forms of a program at once. A run must be at least 5% faster than the reference on all 6 workloads, both in the rewrite-and-rebuild time (which the grader calls congruence) and in the wall-clock time of the whole test process. On the 3 hidden workloads each process takes about 4 ms, and starting the process outweighs the code being optimised. No run passes more than 4 of the 6 wall-clock checks, and three runs pass the congruence check on all 6 workloads.

  9. All 39 queries must be faster, though some have no room

    The task is to rewrite a database's plans for joining tables into faster two-phase plans that filter each table before joining, the method of a PVLDB 2025 paper on the Yannakakis algorithm. The final grade needs the exact result and a lower median time than the reference on every one of 39 queries, 20 public and 19 hidden. On several of them the reference's plan is no faster than the database's original plan, so there is little to gain and a win comes down to timing noise. In 713 evaluations the agents requested during their runs, which use only the 20 public queries, no submission was faster on all 20. Claude Fable 5.1 and Gemini 4 Carbon get every final answer right but are not faster on 14 and 12 of the 39 queries.

The developers' own notes in the task say pass and fail "interleave, so the verdict did not track speed".   11. The video-quality tolerance is tighter than run-to-run noise

    The task is to rebuild the sparse attention of the SVG-EAR paper (ECCV 2026), which makes a text-to-video model faster by skipping part of its attention computation. Each of 12 clips must be at least 4% faster than the reference, and its quality scores against a full-attention video must stay within fixed tolerances of the reference's scores, measured once and frozen. For LPIPS, a measure of how different two images look to a person, the tolerance is 0.005. Two runs of equivalent code differ by up to 0.0056 LPIPS, and the reference's k-means step adds floating-point numbers in a varying order, so its clustering differs between runs. Gemini 4 Carbon is 12% faster and misses the quality tolerances on 4 of the 12 clips.

Other grading errors

These five errors, on four tasks, let a run pass without a better method, grade something other than the paper's method, or count blocked attacks as successful ones.

  1. Copying the reference passes, because ties count

    The task is to find network traffic patterns on which a fast routing shortcut does much worse than the best possible routing, the search problem of the MetaOpt paper (NSDI 2024). On each of 30 test cases, the gap a run finds must be at least as large as the reference's, so ties pass. The reference is deterministic, so a run that copied it would tie everywhere and pass, although none of the released runs does.

    Task: MetaOpt traffic engineering (metaopt_combined_te_gap_search)

    Where: 3 sources
    • Task page on frontier-cs.org: "Find traffic matrices on which a combined heuristic does worst." Task summary and paper: the task's metadata file, lines 4–6
    • judge/evaluator.py:84: candidate >= reference
    • repo/README.md:165-166: "Exact ties pass"

  2. Runs can tune their output to the image being scored

    The task is to restore the training from an ICLR 2026 paper that makes an image tokenizer robust. A tokenizer compresses a picture into a short code of tokens that an image generator works with, and decodes it back. The score is how closely the decoded picture matches the original. At evaluation, a submission can adjust the code by gradient steps toward the exact picture being scored, so the score rewards fitting to that picture rather than a better tokenizer. Gemini 4 Carbon and Gemini 4 Argon (Antigravity) both do this and fail only the speed check.

    Task: Latent-denoising tokenizer (detok_latent_denoising)

    Where: carbon-g (Gemini 4 Carbon), gemini-agy (Gemini 4 Argon (Antigravity)) · 3 sources
    • Task page on frontier-cs.org: "Restore the corruption training that makes an image tokenizer robust." Task summary and paper: the task's metadata file, lines 4–6
    • carbon-g Gemini 4 Carbon · carbon-g.patch:776-812: gradient step on the latents against the input image, called from encode() at eval
    • gemini-agy Gemini 4 Argon (Antigravity) · gemini-agy.patch:267-339: _refine_latents, "refine latent tokens via test-time gradient step through decoder"

  3. The grader trains too little to show the method

    The task is the same image tokenizer, trained with the paper's method of corrupting the code with noise and masking so the decoder learns to repair it. The grader trains each submission for only 16 updates at a learning rate of 1e-6, too little for that training to change anything. Claude Fable 5.1 and Claude Opus 5.5, the two runs that pass under the current grader, win by weakening the corruption and tuning numerical precision and speed.

    Task: Latent-denoising tokenizer (detok_latent_denoising)

    Where: fable51 (Claude Fable 5.1), opus (Claude Opus 5.5) · 4 sources
    • Task page on frontier-cs.org: "Restore the corruption training that makes an image tokenizer robust." Task summary and paper: the task's metadata file, lines 4–6
    • judge/evaluator.py:189-193: one epoch of 64 images at batch size 4, "--lr", "1e-6"
    • fable51 Claude Fable 5.1 · fable51.patch:211-218: "Corruption strength is deliberately mild"
    • opus Claude Opus 5.5 · opus.patch:293-320: 8 to 32 masked tokens and "tau_max": 0.1

  4. The scored games are played before any training

    The task is to turn multi-turn agent trajectories into training batches for RAGEN, a reinforcement learning method for language-model agents from an arXiv 2025 paper, here on a box-pushing puzzle (Sokoban). The grader scores the games the model plays before the one training step runs, so training never affects the score. The reference wins 0 games, and a candidate must beat it on wins and reward in every one of 3 graded groups. No released run wins a game in the second or third group, and the task's README says earlier results "do not establish acceptance".

    Task: RAGEN multi-turn RL (ragen_multi_turn_rl)

    Where: opus (Claude Opus 5.5), sol (GPT-6.1 Sol) · 6 sources
    • Task page on frontier-cs.org: "Turn multi-turn agent trajectories into training batches." Task summary and paper: the task's metadata file, lines 4–6
    • repo/README.md:67-71: "The scored rollouts occur before the optimizer calls"
    • repo/README.md:84: earlier results "do not establish acceptance"
    • judge/evaluator.py:385-386: strict > on success and reward
    • opus Claude Opus 5.5 · one success, on the first graded group only
    • sol GPT-6.1 Sol · one success, on the first graded group only

  5. Blocked attacker calls were counted as successful attacks

    The task is to write the rules from the Progent paper (arXiv 2025) that limit which tools an AI assistant may call, so that instructions an attacker plants in its inputs cannot make it do harm, while it still finishes its real tasks. A run must allow zero successful attacks. Claude Opus 5.5, DeepSeek V4.1 Flash and Qwen 3.8 Max are listed as failing because the grader that scored them counted attacker tool calls their rules had blocked as successful attacks. The task's current grader counts only calls that ran. By our reconstruction of the published traffic, all three have zero successful attacks under that rule and would pass.

Disclaimer

FrontierCS 2 publishes every task, judge, reference patch, final patch and agent trace, so all 48 public tasks could be reviewed; the private set of more than 100 tasks could not. Every error listed above was found by AI review and then hand-checked against the source by a human.

  3. Our computations. vLLM: for each reference run and request group, the geometric mean over requests of that run's latency divided by the per-request target. QuarterPIR: for each query, the median of 5 candidate replays divided by the median of 5 reference replays, from metrics.json in the verifier evidence. Parallel radix sort: the task's score is 100·L/(ln 10 + L), with L the log of the geometric-mean speedup over std::sort on the 8 original workloads; we invert it to turn a score gap into a speed gap. Join-tree and Edlib counts: every evaluation the agents requested during their runs, as recorded in the released traces. These use only the public dev workloads; the final grade adds hidden ones.
